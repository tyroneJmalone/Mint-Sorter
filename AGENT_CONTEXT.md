# Mint PDF Sorter — Agent Context Document

> This document is intended for another agent reviewing this codebase for integration into a broader operations dashboard. It covers the full stack, every processing mode, how data flows, and what would be needed to embed or extend this tool.

---

## What This App Does

Mint PDF Sorter is a PDF processing tool for **Mint Printworks**, a custom apparel/print shop. Their workflow produces two artifacts per job:

1. **Packing slips** — one page per order (or multi-page for large orders), generated by Printavo. Each slip includes customer name, shipping address, garment style/color/size, order number, and optional custom fields (e.g. Department, Homeroom, Team, Location).
2. **Shipping labels** — USPS label PDFs, one label per order, downloaded separately from their shipping provider.

The tool's job is to **sort and match** these two sets of PDFs so the physical stack of labels lines up with the physical stack of slips, ready to go into the box. It also handles edge cases like multi-page slips, label-to-slip name matching, and custom grouping fields.

## API Surface

Base path: `/api` (all traffic routed through a shared reverse proxy on port 80)

### `POST /api/process`

Accepts `multipart/form-data`. Fields:

| Field | Type | Required | Description |
|---|---|---|---|
| `preset` | string (enum) | yes | Processing mode (see Presets section) |
| `sort_fields` | string (JSON array) | only for `custom_sort` | Ordered list of field names to sort by |
| `packing_slips` | file (PDF) | most presets | Single PDF containing all packing slips |
| `labels` | file[] (PDF) | label presets | One or more shipping label PDFs |

Returns:
```json
{
  "jobId": "uuid",
  "outputs": [
    { "key": "sorted_packing_slips", "filename": "sorted_packing_slips.pdf", "label": "Download sorted packing slips PDF", "mime": "application/pdf" },
    { "key": "zip", "filename": "mint_pdf_sorter_outputs.zip", "label": "Download all outputs (ZIP)", "mime": "application/zip" }
  ]
}
```

### `GET /api/jobs/:jobId/files/:key`

Downloads a specific output file. Keys correspond to the `key` field in the outputs array.

**Note:** Jobs are held in memory and their temp files in `/tmp/mint-jobs/<jobId>/`. They are lost on server restart — this is intentional for a stateless processing tool.

## Processing Presets

| Preset | Requires | Produces | Description |
|---|---|---|---|
| `combine_labels` | labels | `combined_labels.pdf` | Merges multiple label PDFs into one |
| `sort_slips` | slips | `sorted_packing_slips.pdf` | Sorts slips: Style → Color → Size → Order # |
| `sort_slips_name` | slips | `sorted_packing_slips.pdf` | Sorts slips: Style → Color → Size → Last Name |
| `sort_slips_custom` | slips | `sorted_packing_slips.pdf`, `custom_field_report.csv` | Sorts slips: Style → Color → Size → Last Name → Custom Field |
| `sort_slips_custom_first` | slips | `sorted_packing_slips.pdf`, `custom_field_report.csv` | Sorts slips: Custom Field → Last Name |
| `sort_labels` | slips + labels | `sorted_packing_slips.pdf`, `sorted_shipping_labels.pdf`, `match_report.csv` | Sorts slips (Style→Color→Size→Order#) then reorders labels to match |
| `sort_both` | slips + labels | same as above | Alias for sort_labels |
| `match_labels` | slips + labels | `sorted_shipping_labels.pdf`, `match_report.csv` | Reorders labels to match slips **in their existing order** (no slip resorting) |
| `custom_sort` | slips + sort_fields | `sorted_packing_slips.pdf`, `custom_sort_report.csv` | Sorts by any user-defined combination of fields |

All presets also produce a `zip` key containing all outputs bundled together.

## Data Extraction — Packing Slips

Each page of the packing slips PDF is parsed independently by `parse_slip_text()` in `processor.py`. The following fields are extracted per page:

| Field | Extraction Method |
|---|---|
| `order_number` | Regex: `Order Number:` or `Order #` |
| `customer_name` | First line of billing block, or first line of page |
| `shipping_name` | First line of shipping block ("Last, First" format) |
| `style` | Product table row: first column = Sort #, second = Style code (e.g. `B5000`) |
| `color` | Product table: appears before qty/price |
| `size` | Product table: standard size tokens (XS–6XL, YXS–YXL, OSFA, OSFM) |
| `custom_field_label` | Anchored after "Recipient Last Name:" block — label varies by job (e.g. "Department", "Homeroom") |
| `custom_field_value` | Paired with `custom_field_label` |
| `delivery_method` | Regex: `Delivery Method:` |
| `location` | Regex: `Location:` or `Location Name:` |
| `sort_number` | First column of product table row |
| `order_date` | Regex: `Order Date:` |

### Multi-page Order Grouping

`group_slip_pages()` groups consecutive pages into logical orders. Continuation pages (no `order_number`, or same `order_number` as preceding page) are attached to the preceding group. All sort operations work on groups — continuation pages always travel with their primary page.

### Size Sort Order

```
XS → S → M → L → XL → 2XL → 3XL → 4XL → 5XL → 6XL
YXS → YS → YM → YL → YXL
OSFA → OSFM
```

## Data Extraction — Shipping Labels

`parse_label_text()` extracts from each label page:

| Field | Method |
|---|---|
| `name` | "SHIP `<NAME>`\nTO:" pattern; fallback: all-caps name line followed by a digit (street number) |
| `address` | Lines following the name |
| `tracking` | USPS tracking number regex (starts with 9xxx, 22+ digits) |

## Label-to-Slip Matching

`match_labels_to_slips()` matches labels to slips using name comparison:

1. **Exact match** — `norm_name(label.name)` == `norm_name(slip.shipping_name)` or `norm_name(slip.customer_name)`
2. **Token subset match** — all tokens from one name are contained in the other (order-independent, min token length 2)

`norm_name()` uppercases, removes non-alphanumeric, and strips stop words (`USA`, `US`, `UNIT`, `APT`, `STE`, `SUITE`).

The match report CSV includes: sequence, status (matched / missing_label / unused_label), method, order_number, style, color, size, slip_name, label_name, tracking, label_source_file, label_source_page, slip_page.

## Custom Sort — Field List and Sort Semantics

The `custom_sort` preset accepts a `sort_fields` JSON array. Available field IDs and their sort behavior:

| Field ID | Sort Value |
|---|---|
| `last_name` | Normalized last name token from `shipping_name` |
| `first_name` | Normalized first name token from `shipping_name` |
| `style` | Normalized style code string |
| `color` | Normalized color string |
| `size` | `(SIZE_ORDER_rank, normalized_size)` — tuple ensures XS < S < M … |
| `custom_field` | Normalized `custom_field_value` |
| `delivery_method` | Normalized `delivery_method` |
| `location` | Normalized `location` |
| `sort_number` | `(0, int)` if numeric, else `(1, normalized_string)` |
| `order_number` | `(0, int)` if numeric, else `(1, normalized_string)` |
| `order_date` | Date string (ISO format sorts correctly as string) |

Normalization (`norm_text`): uppercase, strip non-alphanumeric, collapse whitespace.

The custom sort report CSV always includes all extracted fields regardless of which are being sorted on, so the user can diagnose extraction issues.

## Saved Sort Presets

Custom sort configurations are saved **in the browser's `localStorage`** under the key `mintSortPresets`. Structure:

```json
[
  {
    "id": "uuid",
    "name": "Department then Last Name",
    "fields": ["custom_field", "last_name"]
  }
]
```

There is no server-side persistence for presets — they are per-browser.

## Python Subprocess Architecture

Express calls Python as a child process for all PDF processing:

```
python3 processor_cli.py <preset> <packing_path> <out_dir> [--sort-fields '[...]'] [label_pdf ...]
```

- `processor_cli.py` uses `argparse` to parse arguments and delegates to `process_batch()` in `processor.py`
- stdout is unused; stderr is captured for error reporting
- Exit code 0 = success; non-zero = error (stderr message surfaced to the HTTP response)
- Output files are written to `out_dir`; Express reads the directory after the subprocess exits and registers every file found

Required Python packages: `pdfplumber`, `pypdf`, `pandas`

## Frontend UI Flow

1. User selects a **preset** from a dropdown
2. Contextual file upload zones appear (packing slips and/or labels, depending on preset)
3. For `custom_sort`: a sort field builder appears above the upload zones
   - User adds fields to the sort order list, reorders with arrows, removes with ✕
   - Named presets can be saved to / loaded from localStorage
4. User clicks **Process Files**
5. Files are POSTed as `multipart/form-data` to `/api/process` via raw `fetch` (not the generated hook — generated hooks don't support multipart)
6. On success, per-file download buttons appear plus a ZIP download button
7. Downloads are triggered via `fetch` → `Blob` → temporary object URL → `<a>` click

## Integration Notes for Dashboard

- **Stateless by design** — no database, no auth, no user accounts. Each processing job lives only as long as the server is running. For a dashboard, you would need to either:
  - Embed this as an iframe within the hub (simplest, no code changes)
  - Or add a persistence layer (job store in PostgreSQL/Redis) so results survive server restarts
- **Single-tenant** — currently no concept of users or organizations. All jobs are ephemeral and unattributed.
- **Auth** — none implemented. Adding Replit Auth or Clerk would be straightforward given the Express/React stack.
- **API-first** — the `/api/process` endpoint is fully documented in `lib/api-spec/openapi.yaml` and can be called from any external system (the generated Orval hooks are ready for use in another React app that shares the same base URL).
- **Preset extensibility** — adding a new fixed preset requires: (1) Python logic in `process_batch()`, (2) adding the key to the enum in `openapi.yaml`, (3) running `pnpm --filter @workspace/api-spec run codegen`, (4) adding it to the validator array in `process.ts` and the dropdown in `Home.tsx`.
- **Port / Routing** — API server runs on port 8080 at path `/api`. Frontend runs on port 20707 at path `/`. A shared reverse proxy at port 80 routes by path prefix. In a monorepo dashboard, a new artifact can be added and routed at a different path (e.g. `/mint-sorter`) with no conflict.

## Codegen Workflow

After any change to `lib/api-spec/openapi.yaml`:

```bash
pnpm --filter @workspace/api-spec run codegen
```

This regenerates:
- `lib/api-client-react/src/generated/` — React Query hooks and types
- `lib/api-zod/src/generated/` — Zod validation schemas

Do not change `info.title` in `openapi.yaml` — it controls the generated file naming.
